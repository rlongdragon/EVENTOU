# US-20：跨來源重複活動偵測

同一個活動常被系網、學生會、粉專各發一次。本文件說明重複偵測的流程、分數規則、門檻設定，以及標記配對的驗證結果（NFR-09）。程式在 `backend/src/modules/events/events.dedup.ts`。

同一來源同一網址重跑由 `upsertEvent` 的冪等 upsert 處理，不在這裡。

## 流程

`processAnnouncement` 寫入 Event 後，若活動為已發布、尚未判定過（`dedup_status = none`），而且沒有其他活動合併進來，就做一次重複偵測：

1. **找候選**：開始日期（台北時間）前後 1 天內、**其他已核准來源**、`dedup_status = none` 的已發布活動，排除管理員判定「不是重複」的配對。
2. **算分數**：與每個候選算重複分數，取最高分（同分取 id 較小、也就是較早的活動）。
3. **判定**：

| 分數                     | 結果                                                                  |
| ------------------------ | --------------------------------------------------------------------- |
| ≥ 高門檻（預設 0.75）    | `merged`：合併到既有活動，不再出現在 `published_events`               |
| ≥ 低門檻（預設 0.5）     | `possible`：可能重複，兩筆都照常顯示，交給管理員確認或拆開            |
| < 低門檻                 | `none`：當成新活動                                                    |

已判定為 `merged`／`possible` 的活動，重跑擷取時不會重新判定；保留的那筆（有其他活動指向它）也不會再被合併到別的活動，避免形成鏈。

## 重複分數

| 訊號                 | 分數                                                                 |
| -------------------- | -------------------------------------------------------------------- |
| `registration_url` 相同 | 直接 1 分（比對時忽略 hash 與結尾斜線）                           |
| 標題相似度           | 0.6 × 相似度。標題先 NFKC 正規化（全形轉半形）、轉小寫，去掉標點、括號（如【】）與空白，再算字元 bigram Jaccard |
| `start_time` 完全相同 | +0.3                                                                |
| `location` 相同（正規化後） | +0.1                                                          |

權重定義在 `SCORE_WEIGHTS`。**開始時間不同時最高只有 0.7 分**，低於預設高門檻，所以自動合併一定要開始時間完全相同（或報名連結相同）。這是依 issue「寧可漏判也不要誤判」刻意的設計：誤合併會讓活動從搜尋與行事曆消失。

## 門檻設定

門檻以環境變數設定（NFR-20），範例見 `backend/.env.example`：

| 變數                   | 預設 | 說明                     |
| ---------------------- | ---- | ------------------------ |
| `DEDUP_HIGH_THRESHOLD` | 0.75 | 達到即自動合併           |
| `DEDUP_LOW_THRESHOLD`  | 0.5  | 達到即標記可能重複       |

值必須在 0–1 之間，且低門檻不大於高門檻，否則使用預設值。調整後只影響之後新寫入的活動，已判定的不會重算。

## 資料與顯示

- `events.duplicate_of` 指向保留的活動，`dedup_status` 為 `none`／`merged`／`possible`，`dedup_score` 記錄分數（migration 12）。
- 重複的那筆**保留自己的資料列**（來源與原始連結），所以活動頁可以列出所有來源（`GET /api/events/:eventId` 的 `sources`），還原時也不會遺失資料。issue 原本提的 `event_sources` 表因此沒有另建，避免兩份資料要同步。
- `published_events` 排除已合併的活動。保留的那筆缺 `location`、`organizer`、`registration_url` 時，以合併進來的活動補上；**只在 view 補**，不改寫原始資料，所以重跑擷取不會蓋掉、還原後也自然回到各自的內容。
- 保留的那筆轉為待審（不再發布）時，合併掉的那筆會重新出現在 `published_events`，活動不會整個消失。
- 搜尋、行事曆、通知都讀 `published_events`，所以合併掉的活動自動不會出現在搜尋結果、iCal，也不會寄通知（FR-21）。

## 管理員處理

管理員頁面 `/admin/duplicates`，API 皆需管理員：

- `GET /api/events/duplicates`：可能重複與已合併的配對。
- `POST /api/events/duplicates/:eventId/merge`：確認合併「可能重複」的活動。
- `POST /api/events/duplicates/:eventId/split`：拆開「可能重複」或還原「已合併」（誤合併），兩筆恢復為獨立活動。這組配對會記在 `event_distinct_pairs`，之後重跑擷取不會再合併。

## 標記配對驗證（NFR-09）

`backend/src/modules/events/fixtures/duplicate-pairs.json` 收錄 36 組配對（18 組重複、18 組不重複），由 `events.dedup.test.ts` 用預設門檻計算。配對是依海大各單位公告寫法改寫的**合成範例**，不是實際擷取到的跨來源公告；有實際資料後應補上真實配對重新驗證。

| 指標                                   | 結果             |
| -------------------------------------- | ---------------- |
| 自動合併 precision                     | 12 / 12 = 100%（NFR-09 要求 ≥ 90%） |
| 自動合併 recall                        | 12 / 18 = 66.7%  |
| 合併或標記可能重複的 recall            | 18 / 18 = 100%   |
| 不重複的配對被標記為可能重複           | 6 / 18（交給管理員確認） |

> **待辦**：這組數字來自合成配對，有實際擷取到的跨來源公告後，需改用真實配對重新驗證並更新本表。

自動合併漏掉的 6 組重複都落在「可能重複」，主要是開始時間寫法不同（全天與有時間、報到與開始差 10 分鐘），或標題用語差異大。調整權重或預設門檻時，請更新測試中的預期值與這張表。
